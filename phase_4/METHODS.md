# Phase 4 — how each analysis was done

This document describes, step by step, how every Phase 4 analysis was produced, what its inputs
were, and what it can and cannot support. Numbers live in `results/` (tables regenerated by
`make_summary.py` into `results/FINDINGS.md`); interpretation and headline results are in
`README.md`. Statements are labelled **Observed** (read directly off a result) or
**Interpretation** (reasoning that was not tested).

## 0. Scope

Phase 4 asks *why* the inpainting model underfits (RERUN_PLAN.md Section 10) using only
evaluation of already-trained checkpoints — **no training happens in Phase 4**. All analyses are
on the project's key material: the single song with carved real gaps (Nuvole Bianche), held-out
regions of it, gap lengths 1–4 frames (13–53 ms), which is also the range the models trained on.

Runs analysed (`best_val.pt` unless stated; H1–H3 on all eight plus the STFT-off twin, exp02 on ten):

| group | runs |
|---|---|
| data scaling | `phase1_songs01` (1 song), `phase1_songs04` (4), `phase1_songs17` (17) |
| regularized, 1 song | `phase2_regularization`, `phase3_regularization_seed43`, `phase3_regularization_seed44` |
| 17-song seeds | `phase3_songs17_seed43`, `phase3_songs17_seed44` |
| Phase 0 single-song (exp02 only) | `baseline`, `bigmodel` |
| STFT ablation (Section 7) | `phase4_stft_off_seed43` (H1–H3, audio), compared with `phase3_regularization_seed43` |

`phase1_songs04` and the three regularization runs are the Phase B reruns (decoded-loss
`log_eps` 1e-7 → 1e-3, `grad_clip` 1.5 → 1.0). Their held-out loss is unchanged from the
original runs, so they are comparable to the never-rerun runs.

## 1. Common setup (H1, H2, H3)

1. **Trainer reconstruction.** `phase_0/common.build_trainer(run, checkpoint)` rebuilds a
   `Trainer` through the same `parse_args` path as real training (YAML → config), redirects
   `output_dir` to a scratch folder so nothing under `outputs/runs/` is touched, loads the
   checkpoint, and sets `eval()`.
2. **Held-out examples.** `build_real_validation_examples` rebuilds the exact validation set the
   run used during training (seed `cfg.seed + 1009`): for each activity band (high/low) and gap
   length 1–4, 8 examples taken from held-out regions of the song, i.e. 64 examples. Each example
   is a 512-frame window with the gap replaced by the mask token.
3. **Forward pass for H1/H2.** fp32, no autocast, batch of 1, `eval()` mode. The model returns
   logits that are exactly zero outside the gap; the code asserts this and slices to the gap
   frames before any analysis (an unsliced all-zero row has exactly uniform softmax and would
   masquerade as "mode averaging").
4. **Determinism.** Re-running the `phase1_songs17` diagnostics reproduced the previously
   committed result rows exactly (max abs difference 0.0 over 1,424 rows).
5. **Checkpoint steps:** see the first table of `results/FINDINGS.md`.

## 2. H1 — do the per-codebook heads collapse to the marginal token distribution?

*Question.* Does the model commit to a plausible fill, or does it output something close to the
context-free distribution of tokens?

*Procedure.*
1. Compute, per codebook, three empirical token marginals: **train** (the pivot song with
   held-out regions and real gaps excluded, plus every extra training song), **holdout_all**, and
   **holdout_targets** (the exact target tokens of the evaluated gaps).
2. For each example, gap position and codebook take the model's softmax `p` and record: entropy,
   NLL of the target, top-1 probability, KL(p ‖ train marginal), argmax token, target token.
3. Aggregate per (band, codebook): mean predicted entropy and its ratio to the train-marginal
   entropy; model NLL vs. the NLL of a predictor that always outputs the train marginal; the
   probability that the argmax equals the most frequent training token (and the "lift" over how
   often the target is that token); number of distinct predicted vs. target tokens.
4. A spot check recomputes one NLL by plain indexing and asserts it matches the tensor value.

*Observed.* The model beats the marginal predictor on all 8 codebooks in all runs and bands. In
the high-activity band the margin is small (0.5–1.0 nats) and predicted entropy ≈ the marginal's
(0.89–1.07×); in the low-activity band the margin is 1.3–2.3 nats and entropy is about half. The
argmax is the most frequent token in ≤1.4% (high) / ≤11% (low) of cells.

*Limits.* The train marginal covers all training songs while the evaluated gaps come from
held-out regions of the pivot song only; n = 8 examples per (band, gap length).

## 3. H2 — how does quality vary with codebook index and gap position?

*Procedure.*
1. For every (band, gap length, codebook, gap position) cell record top-1 accuracy (with Wilson
   95% interval), top-5 accuracy, mean NLL, perplexity and mean entropy. n = 8 per cell.
2. Merge over gap lengths (count-weighted) into (band, codebook, gap position) cells.
3. `make_summary.py` reduces this to NLL and top-1 at codebook 1 and 8 per run and band, and the
   least-squares slope of NLL vs. codebook index.
4. **Consistency check against the training-time evaluation.** The per-cell numbers are
   re-pooled with the pooling rule verified against `train.py` (group = mean over cells; band =
   mean over the 4 gap lengths; combined = mean of bands) and compared with (a) an in-process
   call of the trainer's own `run_validation` (fp16 autocast, batch of 8) and (b) the value
   logged in the exported `metrics.csv` at the checkpoint's step. Differences are *reported*,
   never asserted away.

*Observed.* NLL slope per codebook is positive in 8/8 high-activity and 7/8 low-activity run/band
pairs. Pooled fp32 numbers differ from the logged fp16 ones by ≤0.021 nats in six runs, 0.094 in
`phase3_songs17_seed44` and 0.329 in `phase1_songs17`; the in-process fp16 reference reproduces
the logged value to <1e-6, so the difference is a real precision effect and not a pooling bug.

*Interpretation (untested).* A decline across codebooks fits the "independent per-codebook heads
cannot use the residual structure of RVQ" hypothesis, but RVQ residuals also become harder to
predict by construction, so the trend alone does not separate the two. The planned causal test
(H6: condition codebook *k* on the true tokens of codebooks 1..k−1) has not been run.

## 4. H3 — does cross-attention use the context near the gap?

*Procedure.*
1. A forward **pre**-hook on each decoder layer's cross-attention module forces
   `need_weights=True, average_attn_weights=False` (PyTorch's `TransformerDecoderLayer` hard-codes
   `need_weights=False`), and a forward hook stores the weights `[heads, gap_len, context_len]`.
   Handles are removed in `finally` and asserted gone, so the instrumented path can never leak
   into H1/H2.
2. Per run: 2 examples per band, gap length 4, all 4 decoder layers.
3. Each context column is mapped back to its original frame and given a signed distance to the
   nearest gap edge; weights are averaged over heads and query rows within distance bins
   (1, 2, 3–4, 5–8, 9–16, …, ≥257 frames).
4. `make_summary.py` reports the ratio of the mean weight per column at distance 1 to the mean
   weight per column at distance ≥257 (uniform attention = 1×).

*Observed.* The ratio ranges from 5× to ~860× in 30 of 32 (run, layer) pairs; layer 0 of
`phase1_songs17` and `phase3_songs17_seed44` is ≈1× (uniform).

*Limits.* 2 examples per band: illustrative, not a statistical claim.

## 5. H4 — has held-out loss converged?

*Procedure.* Entirely from the exported `phase_{1,2,3}/results/**/metrics.csv` files (never the
raw TensorBoard files). For each run: minimum of `val/combined_loss` and its step; OLS slope of
the last 20 validation points per 100k steps; plateau flag = |slope| < 0.01 nats/100k **and** last
value within 1% of the minimum; where the checkpoint's step also has a `train/avg_nll` point, the
train/val gap at the checkpoint.

*Observed.* No run satisfies the plateau criterion. Held-out loss ends above its minimum in 7/8
runs (+1.03 nats for `phase1_songs01`, +0.29 `phase1_songs04`, +0.12 `phase2_regularization`,
+0.01 to +0.07 for the 17-song runs). The train/val gap is available only for `phase1_songs17`
(0.372 nats).

*Note.* For the Phase B reruns the exported validation losses are unchanged from the originals
(`phase2_regularization` 4.995 vs 4.9936). The launch logs' "Training complete. Best loss" line is
the best *training* loss and must not be read as a validation number.

## 6. Exp02 — which loss term produces the gradient? (STFT-loss evidence)

*Question.* The Phase B' audit of the reruns' aggregated logs counted 10–21% of steps with
`grad_norm > 100` or non-finite, which looked like the decoded-loss (STFT) epsilon problem
persisting. Which loss term actually produces the gradient?

*Procedure* (`exp02_gradient_spike_sources.py`).
1. Build the trainer for a run and load each checkpoint of its entry in `CHECKPOINT_PLAN`
   (best_val, intermediate `step_*.pt` where they exist, final/latest). 26 checkpoints, 10 runs.
2. Put the model in **train** mode (dropout on) and draw 100 batches from the run's own
   training dataloader (same sampler as training).
3. For every batch compute under fp16 autocast, as in training: the token cross-entropy over gap
   positions; the decoded-domain waveform-L1 term; the decoded-domain multi-resolution STFT term.
   The two decoded sub-terms are isolated by zeroing the other's weight in the config (the code
   reads the weights at call time) and each is multiplied by `decoded_loss_weight` exactly as in
   training. The decoded loss itself uses the straight-through estimator (argmax audio forward,
   softmax-weighted codebook embedding backward).
4. Back-propagate each term **separately** with `torch.autograd.grad` (no grad scaler), flatten
   to one vector over all trainable parameters, and record the L2 norm of each, the norm of
   their sum, and whether any entry is non-finite. Also record the model's total weight L2 norm.
5. Summarise per checkpoint (median, p90, p99, max, fraction > 100, non-finite fraction); the
   STFT/token ratio of medians; and, among batches whose total norm exceeds 100, which term
   alone exceeds 100.
6. Write `results/exp02/<run>.json` (per-batch rows), `results/exp02/summary.csv` and
   `results/exp02/gradient_attribution.{png,pdf}`.

*Validation of the measurement.* The measured token-loss norm matches the norm logged during
training at the same step: 53.7 vs 52.9 (`phase3_songs17_seed43` @300k) and 220.5 vs 221.9
(`phase3_regularization_seed43` @300k).

*Observed* (full table: `results/FINDINGS.md`).
- STFT-term norm = 1.5%–6.5% of the token-loss norm at every checkpoint; waveform-L1 < 0.08.
- Token-loss norm grows with training in every run (≈3–9 early → 15–380 late). A `> 100`
  counter therefore fires on every late step once the norm has crossed 100; the reruns' "spike
  rate" is this drift, not isolated outliers. Non-finite steps (~0.045%) are ordinary fp16
  loss-scaler skips and equal in clean and rerun logs.
- Weight norm falls during training in every run with an early and a late checkpoint up to 300k;
  the regularized runs (weight decay 0.1) have the smallest weights and the largest final
  gradients.
- `baseline`'s `latest.pt` (step 162k) has non-finite weights (the run diverged after its best
  checkpoint at 78k), so `best.pt` is its late point. `bigmodel` is finite.

*Interpretation (untested).* With `grad_clip = 1.0` and norms ≥ 3, every step is clipped, so Adam
sees only the gradient direction and the raw norm does not set the step size; this would explain
why changing the clip (1.5 → 1.0) and the STFT epsilon did not change held-out loss. The weight
shrinkage / rising-norm co-occurrence is consistent with weight decay shrinking scale-invariant
weights but was not tested (the 17-song seed-42 run does not fit a simple version of it).

*What exp02 does not show.* It says nothing about whether the STFT loss improves, worsens or does
not affect held-out quality or audio metrics: a term that is small in gradient norm can still
matter in directions the token loss ignores. That question needs the matched training ablation
(`decoded_loss_enabled: false`, same data and seed as `phase3_songs17_seed43`, compared against
the seed noise of ≈0.06 nats / ≈3 dB), which has **not** been run.

*Limits.* 100 batches per checkpoint; one batch element is decoded per step for the decoded loss;
medians over batches, not over training steps; fp16 gradients of the separate terms are computed
without loss scaling.

## 7. Exp03 — STFT-loss training ablation

*Question.* Does the decoded-domain loss (STFT + waveform-L1 on audio decoded from the predicted tokens)
help, hurt or do nothing? Exp02 shows it is a small share of the gradient but cannot show whether it matters.

*Design.* Two runs with the same seed (43), data, model (d_model 128, dropout 0.3, weight decay 0.1),
schedule (300k steps), `grad_clip` 1.0 and validation setup; they differ only in `decoded_loss_enabled`
(`true` for `phase3_regularization_seed43`, `false` for `phase4_stft_off_seed43`). The OFF run's config
was verified by loading both configs and diffing every field: only `config`, `output_dir`, `run_name`,
`device` (cuda:1 launch override) and `decoded_loss_enabled` differ. The OFF run keeps
`validation_audio_metrics_enabled`, so SI-SDR and spectral convergence are still logged.

*Twin check.* The decoded loss starts at step 7000, so before then the runs must coincide; the averaged
training loss agrees to <=5e-5 over steps 1000-7000 (same seed gives the same batches), and the token
loss remains within ~1e-4 for the first 14k steps.

*Comparison* (`exp03_stft_ablation.py`). Reads both TensorBoard logs, pairs the 12 validation points
(25k..300k), and reports OFF minus ON for validation NLL, top-1 accuracy per activity band, gap-only
and total SI-SDR, spectral convergence and training NLL. The noise reference is the standard deviation
across seeds 42/43/44 of the regularization family (`phase_3/results/seed_check/family_summary.csv`).
Rule fixed before the result was known: |difference| < 1 std -> "no detectable effect"; 1-2 std ->
"inconclusive"; > 2 std -> "effect". `--self-check` runs the loader on the ON run alone and confirms it
reproduces the exported seed-check values exactly.

*Observed.* See `README.md` (Exp03) and `results/FINDINGS.md`: every metric is within 0.7 std at the final
step and no validation point exceeds 2 std.

*Limits.* One seed per arm; one weight (0.1); single-song regularized setting only; the noise band
comes from three seeds, one of which (seed 42) used a longer 600k schedule, so it is approximate;
validation uses 64 examples, which makes the audio metrics noisy.

## 8. Not done

- STFT ablation for other settings (17-song models, other seeds, other weights): only the regularized single-song seed-43 twin was run.
- H1–H4 on `baseline` / `bigmodel` (exp02 only).
- H5 (capacity sweep) and H6 (codebook-conditioned heads), both new training.
- Testing why the gradient norm grows (per-layer weight/gradient norms; weight-decay variants).
- n = 8 examples per cell is small; an extended example set was not built.

## 9. Reproduction

```bash
# H1-H3 (+H4 from CSV): all eight runs in one call (the script overwrites results/ each call)
uv run python phase_4/exp01_underfitting_diagnostics.py --device cuda:1 --runs \
  phase1_songs01 phase1_songs17 phase1_songs04 phase2_regularization \
  phase3_regularization_seed43 phase3_regularization_seed44 phase3_songs17_seed43 phase3_songs17_seed44
# exp02 (gradient attribution); add --runs to subset, merged into summary.csv
uv run python phase_4/exp02_gradient_spike_sources.py --device cuda:1
# STFT ablation comparison (after phase4_stft_off_seed43 has trained: configs/train/phase4_stft_off_seed43.yaml)
uv run python phase_4/exp03_stft_ablation.py
# cross-run tables
uv run python phase_4/make_summary.py
```

Inputs the scripts read: the checkpoints under `outputs/runs/`, the YAML configs in
`configs/train/`, and (H4 only) the `metrics.csv` files in `phase_1/results`, `phase_2/results`,
`phase_3/results/seed_check`. H1/H2/H3 need a GPU with a few GB free; the training configs pin
`cuda:0` for several runs, so pass `--device` when that device is busy.
